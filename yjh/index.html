로그로는 확인되지 않는 결함이 세 건 있었습니다. 이미지 로딩 실패를 감추던 처리, 전역 스타일에 가려진 화면 요소, 접두어 기준 필터가 이전 데이터까지 지우던 처리입니다. 모두 결과물을 직접 확인하다 발견했고 이후에는 예외 여부가 아니라 실제 출력으로 확인하는 절차를 뒀습니다.

문제 해결 — 같은 원인의 두 증상

단독 실행에서는 없던 성능 저하가 동시 실행 때 나타났고 오래 켜 둘수록 메모리도 늘었습니다. 별개로 보지 않고 캡처부터 전송까지 흐름을 따라가 같은 구간에서 비롯된 것을 확인했습니다. 이미지를 base64로 바꿔 JSON에 담던 방식을 바이너리 규격으로 교체했습니다.

문제 해결 — 인코딩 경계

한글이 들어가면 서버가 데이터 경계를 잘못 잡았습니다. 헤더 길이를 문자열 길이로 계산했는데 JavaScript의 길이는 UTF-16 코드 유닛 기준이라 UTF-8 바이트 수와 어긋났습니다. 또 검증 스크립트가 HTTP 응답 청크를 문자열로 이어붙여 UTF-8 문자가 경계에서 쪼개지고 있었습니다. 버퍼로 모아 한 번에 디코딩하도록 고쳤습니다.

결과

동시 실행 시 프레임이 약 100에서 150–200으로 올라갔고 틱당 전송량은 약 24% 줄었습니다. 누적되던 메모리 증가도 함께 해결했습니다. 현재 누적 300회 이상 다운로드에 하루 20명 내외가 쓰고 있습니다.

개발 과정에서 관찰한 환경 기준의 수치이며 모든 PC의 성능을 보장하지는 않습니다.

사용자가 기간과 IP를 지정하면 이상 사례를 정리한 보고서가 생기고 그 내용에 관해 자연어로 물어볼 수 있습니다. 라우팅 데이터를 직접 읽어야 했던 과정을 보고서와 질의응답으로 바꿨습니다.

기간
2026.08 – 현재 운영 중
기술

구성
단독 실행 / 상태 파일 기반 / 작업 스케줄러 등록

문제

오픈 시점을 알 수 없어 수시로 들어가 확인해야 했습니다. 단순하게 짧은 주기로 전체 상영표를 받아오면 감지는 빨라지지만 요청량이 그만큼 늘어납니다. 감시 도구가 대상 서비스에 부담을 주는 구조는 오래 돌릴 수 없다고 봤습니다.

한 일

  • 응답 크기가 다른 두 요청을 분리했습니다. 날짜 목록은 0.7KB라 1분마다 받고 전체 상영표는 10분 주기로 돌렸습니다. 새 날짜가 보일 때만 그 날짜의 상영표를 추가로 조회합니다.
  • 첫 실행은 알림을 보내지 않고 기준선만 저장합니다. 이후에는 이전 상태와의 차집합만 알리고 상태를 파일로 남겨 재시작해도 중복 발송이 없습니다.
  • 요청 간격에 난수를 섞고 차단과 오류에 각각 다른 대기 시간을 뒀습니다. 연속 실패가 임계를 넘으면 세션을 새로 엽니다.
  • 하루 두 번 동작 여부를 알리는 신호를 보내 조용히 멈춘 경우를 알 수 있게 했습니다.

결과

분당 요청이 3.6회에서 2.9회로, 시간당 전송량이 약 18MB에서 9MB로 줄었습니다. 같은 기간 새 날짜 감지는 최대 5분에서 1분으로 빨라졌습니다. 기존 날짜의 회차 추가 감지는 10분까지 늦어지지만 급하지 않은 변화라 그쪽을 양보했습니다.

공개된 예매 페이지에서 확인 가능한 상영 일정만 조회하며 예매나 좌석 선점 기능은 없습니다.
